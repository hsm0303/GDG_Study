이번 시간에는 주문 목록을 정상적으로 조회하는 것을 넘어서 조회 SQL의 개수에 대해서 알아보는 시간을 가졌다.
주문 목록 조회에 1개 + 각 주문별로 조회되어져서 발생하는 N + 1 문제에 대해서 알게 되었다.
이를 해결하는 방법으로 Fetch Join, Batch Size 방식이 있다는 것을 알게 되었다.
주문 수를 20건으로 늘려 Fetch Join과 Batch Size 방식을 테스트해보겠다.
Fetch Join은 주문과 주문항목을 함께 조회하는 원리이기 때문에 10건에서나 20건에서나 SQL개수가 1개가 되고 Batch Size는 LAZY 추가 조회를 IN조건으로 묶는 원리를 따르고 위의 실습에 따르면 10개를 기준으로 묶기 때문에 20건에 대해서는 2개로 묶을 수 있으므로 처음 주문 조회를 포함하여 총 SQL개수는 3개가 된다.
Fetch Join의 SQL 개수가 적다는 이유만으로 항상 더 좋은 방법이라고 단정 지을 수는 없다. Fetch Join의 경우 주문행이 주문 항목마다 반복되므로 JOIN 결과 행이 계속 늘어나는 단점이 있기 때문이다. 그런 반면 Batch Size는 반복 SQL를 감소시킬 수 있으므로 필요한 연관 데이터를 이번 조회에서 함께 사용하려고 할 때는 Fetch Join을 사용하고 LAZY를 유지하면서 반복 조회를 줄이고 싶을 때는 Batch Size를 사용하면 된다.
쿼리 튜닝은 데이터베이스에서 발생하는 성능 저하를 해결하기 위한 작업이다.
SQL 개수를 줄이는 것 외에 데이터베이스에서 발생하는 성능 저하를 해결하기 위한 방법으로 3가지 키워드별로 하나씩 방법을 제시하겠다. 
실행 계획의 경우 테이블 전체를 탐색하는 경우가 있는지 확인하는 방법이 있다.
인덱스의 경우 자주 사용하는 조회 조건에 인덱스를 적용하는 방법이 있다.
페이징의 경우 OFFSET 대신 커서 기반 페이징을 사용하는 방법이 있다.
